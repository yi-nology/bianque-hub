# NoSQL 专家模式（Cassandra & DynamoDB）

## 概述

此 skill 为**分布式宽列和键值存储**（特别是 Apache Cassandra 和 Amazon DynamoDB）提供专业的心理模型和设计模式。

与 SQL（您在其中建模数据实体）或文档存储（如 MongoDB）不同，这些分布式系统要求您**首先建模您的查询**。

## 何时使用

- **为规模设计**：超越简单的单节点数据库到分布式集群。
- **技术选择**：评估或使用 **Cassandra**、**ScyllaDB** 或 **DynamoDB**。
- **性能调优**：排查现有 NoSQL 系统中的"热分区"或高延迟问题。
- **微服务**：实现需要高度优化读取的"每服务数据库"模式。

## 思维转变：SQL vs 分布式 NoSQL

| 特性 | SQL（关系型） | 分布式 NoSQL（Cassandra/DynamoDB） |
| :--- | :--- | :--- |
| **数据建模** | 建模实体 + 关系 | 建模**查询**（访问模式） |
| **Joins** | CPU 密集型，读取时 | **预计算**（写入时反规范化） |
| **存储成本** | 昂贵（最小化重复） | 便宜（为读取速度重复数据） |
| **一致性** | ACID（强） | **BASE（最终）** / 可调 |
| **可扩展性** | 垂直（更大的机器） | **水平**（更多节点/分片） |

> **黄金法则：** 在 SQL 中，您设计数据模型以回答*任何*查询。在 NoSQL 中，您设计数据模型以高效回答*特定*查询。

## 核心设计模式

### 1. 查询优先建模（访问模式）

您通常不能"稍后添加查询"而不进行迁移或创建新表/索引。

**流程：**

1. **列出所有实体**（User、Order、Product）。
2. **列出所有访问模式**（"通过 Email 获取 User"、"通过 User 按日期排序获取 Orders"）。
3. **专门设计表**以通过单次查找服务这些模式。

### 2. 分区键为王

数据根据**分区键（PK）**分布在物理节点上。

- **目标：** 数据和流量的均匀分布。
- **反模式：** 使用低基数 PK（例如，`status="active"` 或 `gender="m"`）会创建**热分区**，将吞吐量限制为单个节点的容量。
- **最佳实践：** 使用高基数键（User ID、Device ID、复合键）。

### 3. 聚类 / 排序键

在分区内，数据按**聚类键（Cassandra）**或**排序键（DynamoDB）**在磁盘上排序。

- 这允许高效的**范围查询**（例如，`WHERE user_id=X AND date > Y`）。
- 它有效地为特定检索需求预排序您的数据。

### 4. 单表设计（邻接列表）

*主要用途：DynamoDB（但概念适用于其他地方）*

在一个表中存储多种实体类型以实现预连接的读取。

| PK（分区） | SK（排序） | 数据字段... |
| :--- | :--- | :--- |
| `USER#123` | `PROFILE` | `{ name: "Ian", email: "..." }` |
| `USER#123` | `ORDER#998` | `{ total: 50.00, status: "shipped" }` |
| `USER#123` | `ORDER#999` | `{ total: 12.00, status: "pending" }` |

- **查询：** `PK="USER#123"`
- **结果：** 在**一次网络请求**中获取 User Profile 和所有 Orders。

### 5. 反规范化和重复

不要害怕将相同的数据存储在多个表中以服务不同的查询模式。

- **表 A：** `users_by_id`（PK: uuid）
- **表 B：** `users_by_email`（PK: email）

*权衡：您必须管理跨表的数据一致性（通常使用最终一致性或批量写入）。*

## 具体指导

### Apache Cassandra / ScyllaDB

- **主键结构：** `((Partition Key), Clustering Columns)`
- **无 Joins，无聚合：** 不要尝试 `JOIN` 或 `GROUP BY`。在单独的计数器表中预计算聚合。
- **避免 `ALLOW FILTERING`：** 如果您在生产环境中看到此提示，您的数据模型是错误的。这意味着全集群扫描。
- **写入便宜：** 插入和更新只是对 LSM 树的追加。不要担心写入量，而要关注读取效率。
- **Tombstones：** 删除是昂贵的标记。避免标准表中的高速删除模式（如队列）。

### AWS DynamoDB

- **GSI（全局二级索引）：** 使用 GSI 创建数据的替代视图（例如，"通过日期搜索 Orders"而不是通过 User）。
  - *注意：* GSI 是最终一致的。
- **LSI（本地二级索引）：** 在同一分区内以不同方式排序数据。必须在表创建时创建。
- **WCU / RCU：** 了解容量模式。单表设计有助于优化消耗的容量单位。
- **TTL：** 使用生存时间属性自动过期旧数据（免费删除）而不创建 tombstones。

## 专家检查清单

在最终确定您的 NoSQL 模式之前：

- [ ] **访问模式覆盖：** 每个查询模式是否映射到特定的表或索引？
- [ ] **基数检查：** 分区键是否有足够的唯一值来均匀分布流量？
- [ ] **分区拆分风险：** 对于任何单个分区（例如，单个用户的订单），它会无限增长吗？（如果 > 10GB，您需要"分片"分区，例如 `USER#123#2024-01`）。
- [ ] **一致性要求：** 应用程序能否容忍此读取模式的最终一致性？

## 常见反模式

- **Scatter-Gather：** 查询*所有*分区以查找一个项目（Scan）。
- **热键：** 将所有"Monday"数据放入一个分区。
- **关系建模：** 创建 `Author` 和 `Book` 表并尝试在代码中连接它们。（相反，将 Book 摘要嵌入 Author，或在 Books 中重复 Author 信息）。
