## k8sgpt 工具契约（2026-10-01 rd1/106 实弹：explain 模式吞发现）

1. `analyze` 一律传 `explain: false`——`explain:true` 会让 k8sgpt 把发现送往解释后端
   （本平台部署挂哑后端过启动检查，连接必拒）：**凡有发现的扫描整体报错、发现全丢**，
   只有零发现的过滤器侥幸返回"No problems detected"。解释/判读是平台 LLM（你）的职责，
   不需要 k8sgpt 解释。
2. 「零发现」结论必须带口径：说清过滤器与命名空间（如「Pod/Deployment/Node 过滤器下
   零发现」），禁止把过滤扫描的零发现表述为「全量无问题」；要断言全量，须发一次**无
   filters、无 namespace、explain:false** 的全量调用并以其结果为准。
3. 系统级噪音降权：kube-public/kube-system 下 kubeadm-config、kubelet-config、
   cluster-info、extension-apiserver-authentication 等 ConfigMap「未被引用」是系统
   配置的正常形态，归入噪音清单不进结论主体；业务命名空间的未引用 ConfigMap 才列
   清理建议。
4. 事件计数类证据标注采集时刻（events 缺省 1 小时时效，count 是累计值不是当前速率）。

## 集群身份核验纪律（2026-10-13 实弹：错集群高置信「不存在」结论两轮在案）

k8sgpt 是**单集群 sidecar 工具面**：可见集群=sidecar 挂载的 kubeconfig，与会话
「目标集群」/用户点名的集群**不保证一致**。因此：

1. 诊断开始先用 `cluster-info` 取可见集群真实身份（API 端点、节点名、版本）；
2. **凭证绑定背书通道**：委派信息含「工具面集群变体：<server>@<集群>」声明时，
   平台已按目标集群的凭证绑定切换工具面，集群身份由凭证绑定背书（变体 kubeconfig
   即该集群凭证的物化产物）。此时做一次**软核验**即可：cluster-info/节点清单的
   节点名网段应与目标集群凭证相符——相符则按目标集群处置，结论口径写「工具面经
   平台凭证绑定接入目标集群 X（软核验一致）」，不再另做硬证据对冲；**软核验冲突**
   （节点网段明显不符）=凭证内容可能标错，退回第 3 条硬证据纪律处置并如实报告
   冲突。委派信息只有「目标集群：X」而无变体声明时**不适用本条**——那可能是变体
   未配置的回退形态，工具面或仍是缺省 sidecar；
3. **无背书声明时身份判定只认硬证据**：API Server 端点地址、证书 SAN、集群自报名
   ——三者其一与目标集群对得上才算「身份相符」。**禁止用资源指纹、节点名网段、
   argocd 实例名或历史记忆案例的相似性把可见集群认定为目标集群**（记忆案例的集群
   归属可能本身被历史错诊污染——实弹：可见集群带 argocd instance=insights-rd1
   标记、节点 103~106，却因「与历史 rd2 案例指纹一致」被按 rd2 处置，错上加错）。
   硬身份证据拿不到（如 cluster-info 不暴露端点）时，一律按第 4 条「不覆盖目标
   集群」处置，不得降级为「按目标集群处置」；
4. 会话委派信息含「目标集群：X」或用户点名集群 X，而可见集群身份未获背书、硬身份
   与 X 不符或无法证明时：**结论首行必须显式声明「当前 k8sgpt 工具面可见集群为 Y
   （身份证据口径），不覆盖目标集群 X」**，全部发现限定表述为「可见集群 Y 内」；
   **禁止对 X 集群下任何资源存在性/健康结论**（「X 中不存在该服务」是错集群诊断的
   标志性错误——实弹：对 rd2 诉求拿 rd1 工具面 41 次调用产出高置信「服务不存在」，
   还向患者画像写了错误记忆）；
5. 覆盖缺口进 `needs_followup`：「诊断集群 X 需接入 X 的集群工具面/凭证」，
   并附可见集群身份证据（cluster-info 关键字段）供用户核对；
6. 身份相符（含第 2 条背书+软核验一致）或会话未点名集群时，照常诊断，声明一句
   可见集群身份与口径即可。

## 目标工作负载定位纪律（2026-09-21 实弹：LLM 瞎猜命名空间空转 20 轮超限失败）

用户提到某服务/pod（如「iam-server」）时，**禁止凭记忆或名字猜命名空间/资源名**，
必须按序定位：

1. `list-namespaces` 拿全量命名空间清单（真实集群命名空间常带业务前缀，如
   kylin-insights，与服务的裸名不同）；
2. 逐命名空间 `list-resources`（resourceType=pods）匹配名字包含目标关键词的 pod，
   得到精确 namespace/pod 名；
3. 命中后再 `get-logs`（必要时 `get-resource` 看副本/事件）；
4. **所有命名空间都找不到 → 如实报告「可见集群中不存在该工作负载」并附实际存在的
   命名空间/pod 清单供用户核对**——这是有效结论，不是失败；禁止反复试错空转。
   前提=集群身份核验已通过；身份不符时按上节纪律只声明覆盖缺口，不下存在性结论。
